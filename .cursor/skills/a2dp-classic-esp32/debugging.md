# A2DP log triage

Timestamps in user reports are local. Component tags below are what to grep.

## Symptom → likely cause

| Log / behaviour | Cause | Fix direction |
|---|---|---|
| `i2s_common: i2s_alloc_dma_desc: allocate DMA buffer failed` / `i2s_audio.speaker: Failed to initialize I2S channel` / `Driver failed to start; retrying in 1 second` | I2S DMA needs a **contiguous DMA-capable internal** block. Bluedroid heap in internal SRAM, fragmentation after `speaker->stop()`, or the Classic controller + WiFi eating the DMA pool even with SPIRAM_FIRST. | Keep `bt_allocation_in_psram: true`. Read `dma_largest` from `a2dp` diag. Do **not** overlay `speaker_source`. YAML `CONFIG_BT_ALLOCATION_FROM_SPIRAM_FIRST: y` is necessary, not sufficient. |
| `A2DP audio stopped` then immediately `i2s_alloc_dma_desc` / I2S retry 1s, ACL still up (`sniff` / `hci_status=26`) | Phone paused/stopped SBC. Media source went **IDLE** → stock `speaker_source` `finish()`es I2S. Classic BT still holds internal SRAM so DMA realloc fails. `speaker_source` does **not** finish on **PAUSED**. Sniff `0x1a` is secondary. | On audio stop while `is_connected()`, report **PAUSED** (keep reader in PAUSE wait). IDLE only on ACL drop or explicit STOP. |
| `sendspin.player: Failed to send audio chunk` right after I2S errors | Sendspin still trying to write; I2S never started or already torn down. **Secondary.** Same signature on Sendspin **start** (no A2DP line) is still DMA, not a Sendspin player bug. | Fix I2S/DMA (`dma_largest`). Do not patch Sendspin `STOP`. |
| I2S fails **before** `A2DP audio started` | YAML `bluetooth_connected` → `play_media a2dp://stream` stopped the speaker at **connect**, not at SBC start. | Same DMA/heap issue; switching earlier makes it obvious. |
| `A2DP audio started` then 1–2 s silence, then maybe reboot | Reader counted mixer warm-up `write_output()==0` as dead downstream and called `request_audio_suspend()`. Later Play ignored because source is IDLE. | Keep `ZERO_WRITE_STARTUP_STOP_COUNT`; do **not** auto `play_uri` on `AUDIO_STARTED`+IDLE. |
| `IllegalInstruction` / `__assert_func` / `bta_dm_disable_search_and_disc` | `disable()` deinit while ACL/discovery still live. | Disconnect, finish in `DISCONNECTED`; on timeout leave stack up. |
| `IllegalInstruction` in `esp_vApplicationTickHook` + `__assert_func` + `hci_layer` / `filter_incoming_event` (often `EXCVADDR: 0`) | Abort/assert, **not** a real illegal opcode. TickHook + `esp_restart_noos_dig` are the panic path. Real site is `__assert_func`’s caller. Mixed `btc_a2dp_source_*` + `bta_dm_sdp_result` + `osi_malloc` on a **sink** is typical Xtensa junk after heap smash — IDF compiles A2DP source objects whenever `CONFIG_BT_A2DP_ENABLE` is on; we are not a source. | Same family as DMA-heap starvation. Confirm firmware date vs `disable()` defer + `bt_allocation_in_psram` default. Do not add A2DP source code. |
| `BT_APPL: Pkt dropped` / sequence errors + underruns | Wi-Fi modem-sleep starving the shared radio. | Coexistence `prefer_bt_while_streaming` (disables Wi-Fi PS while streaming). |
| Healthy `rx`, `loop_rate` << ~84/s at 44.1 kHz stereo, ring overflow, `dropped=0` | PSRAM bus contention: ring + BT heap + reader stack all in PSRAM. | Reader `task_stack_in_psram: false`. Keep BT heap in PSRAM. |
| Drain never ends, underrun counter spins | `EVT_CMD_START` still set during drain. | Clear START when setting DRAIN. |
| `[a2dp:…] A2DP audio started` then reboot (`BT_HCI` mode 0, `new conn_srvc id:19`) | `AUDIO_STARTED` issued Wi-Fi PS + AVRCP HCI in the same loop as SBC start → `hci_layer` `filter_incoming_event` abort. Happens with or without Sendspin. | Defer coex 250 ms and AVRCP 1 s after audio start. Do not overlay `speaker_source`. |
| Sendspin plays, web GUI / native API dead, A2DP still discoverable | Classic BT (`auto_start`) + Sendspin Wi-Fi audio share the radio. **Also:** `CONNECTED` used to call `set_coex_preference_(true)` whenever `prefer_bt_while_discoverable` was false (the default), which set Wi-Fi PS to NONE at ACL connect and killed httpd/API before audio. | Prefer BT only from deferred `AUDIO_STARTED`. |

## Heap line

`A2DP audio started (heap_internal=… B dma_largest=… B psram=… B)` and periodic `a2dp: diag: … dma_largest=…`. I2S 100 ms 44.1 kHz 16-bit stereo is ~17 KB of samples plus DMA descriptors — `dma_largest` must stay above that. A large `heap_internal` total with a tiny `dma_largest` means fragmentation.

## Reader diagnostics

With media_source `debug_logging: true`: `loop_rate`, `underruns`, `partial_writes`, `written`, `min_stack_free`. Hub `diagnostics: true`: ring fill, high-water, rx/dropped, heaps, `dma_largest`. Both are low-frequency; leave off in production YAML.

## YAML that must stay aligned

- `a2dp.use_psram: true` (PCM ring) **and** `bt_allocation_in_psram: true` (or omit; default true).
- Do not set `bt_allocation_in_psram: false` on original ESP32 with a live I2S speaker.
- `pause_wifi_sources_on_connect: false` means Sendspin is not paused by the hub; the speaker_source `play_media` still stops the Sendspin **source** on BT connect if YAML does that.
- External component list for HA: `[a2dp, a2dp_sink, a2dp_avrcp]` only — no `speaker_source` overlay.

### 2026-08-26 — `disconnect-fix` won't let the phone disconnect (forces reconnect on explicit phone disconnect)

- **User report:** on `disconnect-fix`, if the phone explicitly disconnects A2DP (user taps "Disconnect" in the phone's Bluetooth UI), the sonnocotta device does not let go — it forces the phone to reconnect.
- **Cause:** `ESP_A2D_CONNECTION_STATE_EVT`'s `param->conn_stat.disc_rsn` (`ESP_A2D_DISC_RSN_NORMAL` = graceful teardown initiated by either side, `ESP_A2D_DISC_RSN_ABNORMAL` = signal loss) was read from the ESP-IDF callback but **discarded** — `handle_a2d_event_()` never copied it into the queued `A2DPEventRecord`. The `loop()` `DISCONNECTED` handler then scheduled `reconnect_at_` (auto-reconnect, `RECONNECT_INITIAL_DELAY_MS` = 1 s) unconditionally whenever `enabled_ && auto_reconnect_ && has_last_peer_`, with no way to tell a graceful phone-initiated disconnect apart from an actual link loss (e.g. Wi-Fi-interference supervision timeout, the case the retry logic was built for). The ESP32 then calls `esp_a2d_sink_connect()` back at the phone, which a previously-paired/trusted phone typically accepts — looking like the device "won't let go".
- **Not a regression from our own `disconnect()`/`disable()`:** those already set `connected_ = false` synchronously before the event queue is drained, so the `if (this->connected_)` gate around the reconnect logic already skips them. Only *remote*-initiated graceful disconnects were affected.
- **Fix (`a2dp.cpp`/`a2dp.h`):** added `esp_a2d_disc_rsn_t disc_rsn` to `A2DPEventRecord`; `handle_a2d_event_()` now copies `param->conn_stat.disc_rsn` into it. `loop()`'s `DISCONNECTED` case only schedules the reconnect (and `resume_playback_on_reconnect_`) when `ev.disc_rsn == ESP_A2D_DISC_RSN_ABNORMAL`. On `ESP_A2D_DISC_RSN_NORMAL`, no reconnect is scheduled, but `start_discovery_()` still runs so the device stays passively connectable.
- **Next evidence:** flash this commit; explicitly disconnect from the phone's BT settings and confirm no `Reconnect to last A2DP source requested` log follows (should instead see `Graceful disconnect — not auto-reconnecting`). Separately confirm a real link-loss (e.g. walk phone out of range, or Wi-Fi-heavy load) still triggers the retry sequence as before.

Action item is operational: point the remaining device YAMLs at `@disconnect-fix` and reflash, and consider backporting/merging into `main` since it is otherwise unmaintained relative to `disconnect-fix`.

### 2026-08-25 — OPEN QUESTION: long standby (≈1 day) on `main`, phone connects but stays silent, no log, needs reboot

- **User report (no log captured):** after ~1 day of standby on `main`, the phone could connect via A2DP, but playback never started / stayed silent. No app-level log at all. Only an ESP32 reboot fixed it.
- **Code comparison `main` vs `disconnect-fix`:** on `main`, `DISCONNECTED` does **not** schedule a reconnect — it just calls `start_discovery_()` and passively waits for the peer. `disconnect-fix` actively retries `esp_a2d_sink_connect()` (`reconnect_to_last_peer_()`, up to 5× / 3 s) and remembers `resume_playback_on_reconnect_` to send an AVRCP PLAY on the next `AVRCP_CT_CONNECTED`. Neither branch has any watchdog for "`CONNECTED` fired but `AUDIO_STARTED` never followed" — there is no code path on either branch that would catch or self-heal this specific state, and no app-level event fires in that state (Bluedroid's own AVDTP/BTA layer is closed-source and silent by default), which matches "no log at all".
- **Assessment:** most likely **not** something introduced or removed by any commit tracked in this log. The "connects but the AVDTP media stream never opens" failure is a well-known class of ESP-IDF Bluedroth/AVDTP issue (stale stream-endpoint/control-block state after many hours of uptime, or simply the phone-side app not sending `AVDTP_START`) that neither branch currently detects or recovers from without a full reboot. `resume_playback_on_reconnect_`/AVRCP-PLAY only fires on the "unexpected disconnect while streaming, then reconnect" path — it would **not** trigger for a fresh first-connect-of-the-day with no prior stream this session, so it would not have helped this specific report even on `disconnect-fix`.
- **Ruled out:** claiming disconnect-fix already fixes this — no evidence either way; do not present it as fixed without a captured log.
- **Next evidence (before rebooting next time):** capture the log at the moment of the failed connect. Check whether `[I] BT connected` and `AVRCP CT connected` appear; if so but `A2DP audio started` never does, that isolates it to the AVDTP media-stream layer (not our app code). Raise `logger` verbosity for `BT_APPL`/`BT_AV`/`BTU_TASK` if possible. Enable `diagnostics: true` to see `connected`/`audio_streaming` state at the time.
- **Proposed (not yet implemented, needs user go-ahead):** add a "connected but never streamed" watchdog in `a2dp.cpp` — if `connected_` stays true for N seconds without `AUDIO_STARTED`, proactively `esp_a2d_sink_disconnect()` + reconnect to force a clean AVDTP renegotiation, avoiding the need for a physical reboot. This is a new mechanism, not a regression fix — needs explicit sign-off before implementing.

### 2026-08-25 — A2DP never takes over from Sendspin (stuck IDLE); Sendspin stutters while A2DP streams

- **Logs (nappali):** Sendspin playing fine (flac, sync OK). `[I][a2dp:330] A2DP audio started (heap_internal=25564 B dma_largest=21504 B psram=…)` — DMA succeeded (`dma_largest` > 20 KB). **No** `speaker_source_media_player: State changed to …` follows it — the orchestrator never switches. User: phone playback does not take over the speaker; Sendspin starts stuttering while A2DP streams; stopping A2DP restores Sendspin. Then sustained `BT_APPL: Sequence numbers error` / `Pkt dropped` (BTU_TASK/BTC_TASK) for the rest of the A2DP session, ~1 min later, not just at start.
- **Cause (switch failure):** the only trigger was the `bluetooth_connected` binary_sensor's `on_press` YAML automation, which fires only on the ACL connect **edge**. If the ACL was already up (e.g. `auto_reconnect`, or the a2dp media source went **IDLE** on a previous stop before the PAUSE-not-IDLE fix existed) and the phone starts a **new** playback session without a fresh ACL connect, that automation never re-fires and nothing calls `play_uri`. A2DP audio flows into the hub PCM ring anyway (hence `A2DP audio started`) but never reaches the speaker; Sendspin keeps DAC ownership while the BT radio is now also busy decoding A2DP → Sendspin stutters until A2DP stops.
- **User constraint:** live HA YAML is read-only from this checkout (root-owned on the CIFS mount) and the user does not want a per-device YAML workaround anyway — the fix must live in the `a2dp`/`a2dp-sink` component so it ships via `github://cociweb/a2dp-sink@disconnect-fix` without touching any device YAML.
- **First attempt (reverted):** a YAML `a2dp_sink.on_audio_start` automation guarded by `get_state() == IDLE` before calling `media_player.play_media`. Worked in principle but violated the "must not touch YAML" constraint, so it was reverted in favor of the component-level fix below.
- **Ruled out:** `speaker_source` overlay; a raw/direct `play_uri()` call from inside the `AUDIO_STARTED` callback (the *original* banned pattern — bypasses the orchestrator's arbitration entirely and can steal Sendspin mid-stop). `try_execute_play_uri_()` **always** stops-then-restarts the target if its state isn't IDLE, even when it's already the correct active/playing source — so unconditionally requesting play on every `AUDIO_STARTED` would forcibly `STOP`→`finish()` I2S on every track/resume and reopen the DMA-realloc bug the PAUSE fix just closed. Hence the `get_state() == IDLE` guard is still required, just moved into the component.
- **Fix (component, `a2dp_sink_media_source.cpp`/`.h`):** in the `audio_streaming` callback, when `streaming == true` and `get_state() == IDLE`, call `this->request_play_uri_(A2DP_URI)` — the same sanctioned "orchestrator, please play me" mechanism `SendspinMediaSource::on_stream_start()` already uses for itself. This queues through the normal control path (`try_execute_play_uri_` stops whatever is currently active first); it is **not** a direct `play_uri()` call, so it doesn't bypass or race the orchestrator like the original banned attempt did. A `auto_play_pending_` bool dedups repeated `AUDIO_STARTED` blips (e.g. sniff-exit) so we don't spam the control queue before the first request is processed; it's cleared once `play_uri()` actually runs or on `STOP`. Still does nothing while `PLAYING`/`PAUSED` — no change to the resume-from-PAUSED or drain/pause paths.
- **Pkt dropped / Sequence numbers error:** Matches the existing coexistence row. `prefer_bt_while_streaming: true` is already set; the drops are sustained through the whole A2DP session, not just at start, so this looks like a genuine BT/Wi-Fi radio time-share limit rather than something the current coexistence knobs fully solve. Not touched further — no new architecture without more evidence (e.g. does it still happen with Sendspin idle / no Wi-Fi traffic?).
- **Next evidence:** Flash `disconnect-fix` at/after this commit. Confirm `speaker_source_media_player: State changed to PLAYING` now follows `A2DP audio started` even when ACL was already connected, and that it does **not** thrash (repeatedly stop/restart) if the phone briefly drops in/out of sniff while already playing. If `Pkt dropped` persists with Sendspin fully idle, that isolates it to BT-only radio contention (e.g. AVRCP/attribute polling), not Wi-Fi.
